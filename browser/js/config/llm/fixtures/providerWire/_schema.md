# providerWire fixtures — llm-contract.md §6 wire-mapping conformance vectors

Golden request/response vectors for the three provider mappings every surface
hand-rolls (contract §6.1 ollama, §6.2 openai-compat, §6.3 stencil-server).
Generated by running the browser reference implementation
(`browser/js/llm/client.js`); the JSON here is literal — no generation at test
time. Walked by `browser/tests/llm/llmWireFixtures.test.js`; other surfaces add their
own walkers against the same files.

Every `*.json` file in this directory is an array of case objects:

| field | req | meaning |
|---|---|---|
| `name` | yes | unique within the corpus; `DIVERGENCE(...)` prefix marks known cross-surface differences |
| `comment` | no | prose for humans; never asserted |
| `divergences` | no | informational inventory `{ "<surface>": "one-line summary" }` of measured surface differences on this case; never asserted — walkers ignore it. The pinned surface-specific values themselves live in each surface's local override file |
| `provider` | yes | `"ollama"` \| `"openai"` \| `"server"` (→ §5 `ollama` / `openai-compat` / `stencil-server`) |
| `settings` | yes | the §5 config subset used: `baseUrl`/`serverUrl`, optional `model`, optional `apiKey` |
| `token` | server only | the existing Stencil session bearer `getToken` resolves |
| `chat` | yes | `{ system, messages }` in the canonical form: `[{ role, text, images?: [{mediaType, data}] }]` |
| `expectUrl` | yes | full request URL (`{baseUrl}/api/chat`, `{baseUrl}/chat/completions`, `{serverUrl}/llm/chat`) |
| `expectAuthorization` | no | exact `Authorization` header value; **absent means the header must not be sent** |
| `expectBody` | yes | the exact JSON request body — compare with DEEP EQUALITY, field absence is part of the contract (e.g. `maxTokens` is never sent, server `model` is omitted when empty) |
| `response` / `errorResponse` | one of | `response` = 200 body; `errorResponse` = `{ status, body }` where a string `body` means a non-JSON payload |
| `expectReply` / `expectError` | one of | `expectReply` = extracted reply text; `expectError` = `{ kind, message, status? }` (kinds: `truncated`, `refusal`, `disabled`, `badReply`, `http`) |

Walker mechanics (any language): build the request with your client pointed at a
capturing transport, deep-compare the body against `expectBody`, then feed it
`response`/`errorResponse` and compare the extracted reply or typed error.
`expectError.message` is post-sanitizer text — a walker whose sanitizer diverges
(see `../sanitizer/_schema.md`) may relax `message` to its own sanitizer's output
but must keep `kind`/`status`. `badReply` messages carry the browser's phrasing;
a surface with its own bad-reply wording keeps the `kind` and asserts its own
message (the phrasing drift is inventoried in `divergences`). All requests are POST + `Content-Type:
application/json`, non-streaming.
